# Environment configuration

Use one server configuration, `.env.local` at the repository root. Generate it
with `infra/deployment/new-depo-deployment-config.ps1`; it reads
`config/deployment.env.example` and generates distinct bootstrap secrets. The
generator refuses to overwrite an existing file unless `-Force` is supplied.
Start services through the deployment lifecycle script with `-EnvFile .env.local`.

| Template | Purpose | Destination |
| --- | --- | --- |
| `deployment.env.example` | Required service and database configuration | Root `.env.local`, generated by the configuration script |
| `spark.env.example` | Optional Spark settings | Merge selected settings into root `.env.local` |
| `../frontend/.env.example` | Public browser settings | `frontend/.env.local` |

The Spark template is not loaded automatically. Do not overwrite configured
credentials with its blank values. Update existing keys instead of appending duplicates;
the shared parser rejects duplicate keys before changing the process environment. The browser configuration is intentionally
separate: Vite compiles these values into public JavaScript. Never copy the
server configuration into the frontend or put secrets in `VITE_*` or
`REACT_APP_*` variables. Rebuild the frontend after changing its configuration.

The lifecycle launcher loads the selected server file into child-process
environment variables. Direct Python invocations do not automatically load
root `.env.local`; inject the equivalent environment explicitly. Legacy database
helpers still accept `.env` defaults with `override=False`, so existing process
values take precedence. Remove stale local legacy files after migrating their
required settings; the retired templates are no longer distributed.

For production, inject equivalent settings using the deployment secret manager.
See the [deployment guide](../infra/deployment/README.md) for validation and
authentication profiles.
