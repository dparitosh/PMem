## Original high-priority defects — corrected in the follow-up

### 1. Bridge publication reports success after its graph data has been reset

- Evidence: `backend/agentic_service/bridge_jobs.py:146` returns a cached published job before checking the graph receipt. `backend/depo_platform/maintenance.py:40` invalidates only `ontology_graph_publications_v1`, leaving `semantic_bridge_jobs_v1` untouched.
- Trigger: publish a semantic bridge, reset the graph through Admin, retry the saved publication.
- Impact: UI/API report completed mapping although the receipt and mapped relationships no longer exist; retry cannot restore them.
- Verification: executed the actual `BridgeJobs` implementation with existing in-memory test fixtures. Cleared graph receipts after publication, then retried. Result: `status=published`, `graph_receipt_exists=False`, `total_publish_calls=1`.
- Correction: invalidate affected bridge jobs during reset and check authoritative graph receipts before returning cached completion. Require a fresh preview where reset changed source/target identity.

### 2. Bridge publication cannot authenticate through subscription-protected APIM

- Evidence: `backend/agentic_service/bridge_jobs.py:307` sends only Authorization. The existing `backend/depo_platform/network.py:8` helper provides the configured gateway subscription header, and other service clients use it.
- Trigger: `GRAPH_SERVICE_URL` points to the configured subscription-protected gateway with `DEPO_APIM_SUBSCRIPTION_KEY` supplied.
- Impact: both publication and receipt reconciliation fail despite valid configured credentials, blocking the semantic bridge workflow.
- Verification: inspected the complete request construction and shared header helper; live gateway validation remains pending.
- Correction: reuse the existing service authentication/header helper with the full destination URL, preserving gateway origin/path checks.

### 3. Initial PostgreSQL heartbeat failure terminates the pipeline worker

- Evidence: `backend/data_pipeline_service/worker.py:25` writes worker status before entering the guarded claim/retry loop. Startup launches a process through `infra/windows/start-depo-services.ps1:158`; its worker checks detect exit but do not restart it.
- Trigger: PostgreSQL is temporarily unavailable or rejects the initial heartbeat when the worker starts.
- Impact: the worker exits instead of recovering; queued data jobs remain unprocessed until an operator restarts it.
- Verification: control-flow inspection; runtime outage injection against PostgreSQL remains pending.
- Correction: move initial registration into the retry lifecycle with bounded backoff and expose unavailable readiness until registration succeeds.

## Archive security defect — limit added; live route validation pending

### 4. ReqIF ZIP expansion has no decompressed-byte budget

- Evidence: `backend/Services/unified_data_import.py:781` calls `archive.read()` on the selected XML/ReqIF member before parsing. No member-size or expansion-budget check protects this operation.
- Trigger: a compressed ReqIF upload expands to a very large XML member.
- Impact: excessive allocation can terminate or severely degrade the ingestion process. Compressed upload size alone does not bound decompressed size.
- Classification: P1 if this ZIP parser is reachable through the deployed upload route; otherwise latent security defect. Route reachability and resource exhaustion were not demonstrated during this review.
- Correction: reuse archive validation, bound entry count and total/member expanded bytes, and enforce the budget while reading rather than relying only on ZIP metadata.

## Candidates not counted as confirmed P1

- Full graph reset and graph publication have no apparent shared maintenance fence. Concurrent execution needs a controlled integration test to establish the precise corruption window.
- Product download checks package integrity but not revoked lifecycle. Verify whether retained revoked packages are intentionally readable for audit before changing or classifying that behavior.
- The maintenance cleaner appears to require a password even for passwordless Neo4j deployments. Assess supported deployment scope before assigning priority.
