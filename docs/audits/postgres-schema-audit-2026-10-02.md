# PostgreSQL schema audit — 2026-10-02

> Dated audit record: use [the current audit index](README.md) for latest validation and acceptance status. Findings and test counts below belong to their recorded review; they are not a current release certificate.

Scope: SQL migrations 000–006, schema setup/verification, PostgreSQL registry/runtime/metadata consumers and schema-only PowerShell wrappers. This audits repository code; the customer's live database was not inspected.

## Confirmed findings

1. **P1 — Verification occurs after migration commit.** `backend/depo_platform/database_setup.py:138-143` closes the migration transaction before verify_schema. Migrations 001–003 use CREATE TABLE IF NOT EXISTS, so an incompatible pre-existing relation can be skipped while its migration version is committed. Verification then fails, but subsequent installs skip those recorded versions. Verify inside the same outer transaction so DDL and migration history roll back together on an incompatible schema. Do not delete customer tables to recover.
2. **P1 — Constraint/index names can produce false schema approval.** `database_setup.py:102-114` checks names only. It does not verify relation ownership of each constraint/index, key columns, FK targets, CHECK expressions, constraint validation, index predicate or index validity. A same-named weaker/wrong index or constraint can pass. Verify pg_constraint/pg_index definitions and flags against each owned table's contract.
3. **P2 — Required column attributes are not verified.** `database_setup.py:94-99` checks data_type only. Nullable required columns, missing updated_at/applied_at defaults and a broken message_id sequence/default can pass then fail at inserts or admit invalid rows. Verify nullability, defaults, generated/identity/sequence behavior and relation kinds. Preserve compatibility with the intended BIGSERIAL sequence rather than requiring only IDENTITY.
4. **P2 — Migration content drift is undetected.** `backend/postgres_migrations.py:40-54` records version/name only. Editing SQL under the same version/name is silently skipped on redeployment. Store and verify a checksum of immutable migration contents, with an explicit trusted upgrade policy for historical rows that lack checksums. Do not rewrite applied migrations to repair existing installations; add a new migration.
5. **P2 — Registry/runtime JSON column shape is unconstrained.** Migrations 001/002 declare value JSONB NOT NULL but do not require an object, unlike metadata tables in 003. Runtime consumers call .get and JSON object updates on those values. Add object-shape validation in writers and versioned CHECK constraints after diagnosing existing scalar/array rows. Namespace-specific timestamps should also be validated before workers/expiry cleanup cast them; a generic JSONB column alone cannot enforce every namespace contract.
6. **P2 — Common registry history queries lack a matching index.** `backend/mesh_store.py:57` filters namespace and orders updated_at DESC; the primary key is namespace,key and migration 006's index covers only runnable pipeline records. Agent telemetry and retained product/ontology/run history can require large scans/sorts. Add a generic namespace,updated_at DESC,key index and a deterministic ordering tie-breaker. Confirm effectiveness with EXPLAIN on representative customer data before claiming a performance result.
7. **P2 — Migration and legacy runtime statements lack database deadlines.** `database_setup.py:132` and `backend/Services/runtime_state_store.py:20-26` set connection timeouts, but not statement/lock deadlines. DDL or advisory-lock waits can hang installation or compatibility requests after a connection succeeds. Apply separate configurable statement/lock limits appropriate to migrations and runtime work; the recent registry timeout fix does not cover these connection paths.
8. **P2 — Analytics relation definition is not verified.** Verification accepts the analytics relation's column names/types but does not ensure it is the expected view or that it filters namespace=ontology_catalog. A stale/replaced view or same-shaped table can pass while reports use the wrong data. Verify relation kind and normalized view definition/dependencies. Current depo_ontology_analytics is an ontology-statistics projection, not a dimensional analytics warehouse; fact/dimension tables are not present in these migrations.

## What is present and sound

The release owns eight tables and one analytics view: depo_schema_migrations, depo_registry, depo_runtime_state, depo_chat_messages, depo_rate_limits, depo_metadata_assets, depo_metadata_events, depo_metadata_outbox and depo_ontology_analytics. Verification declares 40 columns, 15 constraints and four named indexes across six versioned migrations. Migration discovery requires contiguous versions and rejects unknown database versions. Migrations use a transaction and schema-scoped advisory lock; metadata asset/event/outbox writes are transactional, revision-checked and asset-lock serialized. SQL values use driver parameters. Schema identifiers are bounded and quoted. Bootstrap provisioning gives the application its schema without database ownership.

## Verification and limits

A direct execution of the current verifier with its expected catalog rows returned status=ok and demonstrated that it never requests nullability/default/identity metadata or constraint/index definitions. Migration history has no checksum column. This confirms verification omissions, not actual corruption in the customer database. No PostgreSQL server or application dependencies were installed, no customer data was queried, and no application code changed during this audit. Fixes need migration rollback/drift regression tests and real PostgreSQL upgrade tests before customer release.


## Fix implementation

All eight audit findings have code fixes: verification inside the migration transaction, catalog definition/validity checks, required column/default/owned-sequence checks, immutable SQL checksums with explicit historical adoption, migration 007 object checks plus application writer guards, generic history index and deterministic ordering, separate migration/runtime statement deadlines, and relation-kind/view-definition verification. Existing migration SQL 000–006 was preserved. The resulting contract is 41 columns, 17 constraints and five named indexes, with versions 1–7.

Focused tests verify rollback on structural failure, checksum drift/adoption, required attributes, invalid constraints/indexes, wrong views/sequences, JSON writer rejection and Windows newline checksum stability. Database-dependent upgrade tests remain pending: no PostgreSQL server was installed or customer database contacted. The existing pytest suite was updated for the contract but pytest is absent from the cleaned environment. Commit and push status is recorded in Git.
